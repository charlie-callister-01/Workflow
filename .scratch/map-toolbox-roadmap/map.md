## Destination

`notes/roadmap.md` v1: a phased roadmap for evolving this Workflow repo, with Phase 1 sliced into concrete changes and the big questions decided (which outside methods to adopt, multi-agent projects, repo profiles and change flows, what happens after wayfinder and after implementation, the learning section, artifact organisation, the evolution loop, a status page). The toolbox is ongoing; this map ends at roadmap v1. The roadmap describes **v2**; v1 (tag `v1.0`, `notes/v1.md`) stays as it is apart from fixes.

## Notes

- Domain: this repo, Charlie's personal toolbox of skills, presets, platforms, templates and notes, used to set up new projects and bring existing ones in line. Evolve it. Since 35 it has two private neighbours, the home repo (where sessions start) and the knowledge repo (replacing the vault), set up outside this map.
- Plan, don't do: tickets produce decisions. Changes happen afterwards through `feature/...` -> `/open-pr`.
- Override: research findings are kept, not thrown away. Each research ticket writes `notes/research/YYYY-MM-DD <topic>.md` (format in `notes/research/README.md`) on the map's branch; no `research/` branches. Since the refit (2026-11-24), research mostly runs **inside** a grilling session: a subagent limited to the primary sources fetches the fact a question needs and returns a short summary, with a research note only when the findings are worth keeping.
- **Sources.** Primary: **Pocock** (the base), **Osmani**, **pstack / fstack** (with Flavio Copes), **ICM** (from 40). Parked, ticketed only when the owner picks one: superpowers, Spec Kit, OpenSpec, Compound Engineering, BMAD, GSD Core, anthropics/skills, the two books. 05's adoption table stays the record of what was adopted; picks add rows to it.
- **Main takeaways** (the owner's must-haves, to use across the workflow; guidance, not a checklist every task must tick, and not the only things worth taking):
  - pstack / fstack: **heavy verification above all: every task gets a goal and a way to check it, and the check is run and shown**; a "what we're NOT doing" section; a three-question check before ship; loops need a finish condition and a decision log; keep dismissed findings with reasons; prototype instead of asking when running something would settle it.
  - Osmani: a skill is a process with a hard verification exit, not prose; the meta-skill (`using-agent-skills`: a router plus five non-negotiables); scope discipline, touch only what was asked; every `AGENTS.md` line traces to a real failure (~60 lines); rules that must hold go in checks, not prose; prune configuration by experiment; doubt-driven review for high-stakes decisions.
  - Pocock: grilling with a recommendation per question; wayfinder maps for foggy work; one vocabulary in `GLOSSARY.md`; spec, then tickets, then build test-first; fresh-context subagents to protect the main context; `retro` as the ratchet's review.
  - ICM (from 40): **context in layers, injected per stage**: read down from `AGENTS.md`, stop when you have enough, load only what the stage's contract lists (section scope, not whole files); **every stage leaves a plain, reviewable file** (observable by default; git is the only trace); stage folders with `CONTEXT.md` contracts for **planning artifacts only**, on trial before adoption; one-way links, one canonical home per fact, audit tables before saving.
  - The owner's own (2026-11-25): **complementary reviewers and doubt-driven design**: review from more than one fresh context, each with its own angle (as `/code-review`'s two axes, the architecture review and the strict written-work review), and before a plan or decision is accepted a separate context tries to disprove it (Osmani's doubt-driven review, the `doubt` grilling style).
  - The owner's own (2026-11-26): **build in stages, as modules, with guides, settings, a trace and an evaluation**. No decision is built all at once: each reaches projects in stages, a beta trial first (17), promoted once its evaluation passes. Each system is **a module**: adopted, switched off or removed on its own, its dependencies on other modules stated, with nothing silently relying on another, so the workflow can be assembled per project and changed a piece at a time. Every built module comes with:
    1. **A guide**: what it is, why, how to use it, how to configure it and how to tell whether it is working, written for someone learning it.
    2. **Settings** in plain files to turn it up, down or off per project (as 31's Checks section).
    3. **A visible trace**: what it did and which settings applied (a file, a PR section, a LOG line or a commit).
    4. **An evaluation**: what to watch during the trial, the pass condition and what was learned, fed into 09's loop, so the best way to use it is found by experience rather than assumed.
  At the last session (Roadmap v1) these move into `notes/roadmap.md` as its standing principles.
- **Session opening: the picks panel.** Each grilling session starts with a table, Source | What it does about this question | Note | Owner's call (pick / reject / park + reason), one row per primary source that has something to say (none padded), with a short explainer under any finding that really matters. The answer records the calls under `Picks`, with a line on what was taken from each source; dismissed lines keep their reason. Research reaches a ticket only through the owner's picks; "From NN" notes carry decisions, not research.
- Claude Code is the main agent for now, but a project may use other agents (Cursor, Codex, Copilot), several at once. Since 35: agent-agnostic by default (plain files, scripts, git hooks and CI first; no plugins; Claude-only settings only as an optional extra).
- Grilling tickets: call the grilling and domain-modeling skills. Decisions with a real trade-off go to `notes/decisions/NNNN-*.md`. Each carries a `Style:` line (the owner may change it at the start): `rounds` (Pocock, default: the design tree, a round at a time, each with a recommendation), `nail` (fstack: at most 5 questions, then a 3-line summary to approve), `interview` (Osmani `interview-me`: one question at a time until confident, for the owner's own preferences), `doubt` (rounds, then a fresh-context subagent tries to disprove the summary before it resolves; dismissed objections kept).
- Open items in `notes/ideas.md` are absorbed here (tickets or fog); `ideas.md` stays the inbox for new ideas.
- Vocabulary is in `GLOSSARY.md` (decision ticket vs work ticket, repo profile vs change flow, ...). Grilling tickets add to it as terms settle.
- Pace: slow and tested. v2 changes reach projects as trials (`beta/` folder, `notes/trials.md`): beta skills install side by side as `<skill>-beta`, templates go on a per-project beta track (17), then get promoted to production. Principles in `DEVELOPING.md`, "Pace and release tracks"; mechanics in decision ticket 17.
- Projects must never end up carrying files or skills they don't use: every v2 proposal says what lands in a project and why. Since 35, no project carries toolbox skills (home copies them in), and every session starts in home: proposals say how they work from there (36).
- Order (refit 2026-11-24; foundations 36, 06, 07, 17, 23, 30 done; 41 and 42 added 2026-11-25; 40, 41, 42, 31, 15 and 34 done 2026-11-26; 37, 39, 09 and 10 done 2026-11-27): **14 closing work, next**; then Directory and design (fog); last, the roadmap itself (fog: Roadmap phases). Blocked-by lines hold only real dependencies, so pick from the frontier in this order, not first number first. The refit merged 32 into 37, 19 into 34, 16 into 39 and 21 into 09, split 15 (PR lifecycle) from 39 (session state), and removed fog that was answered or is doing rather than deciding (see Roadmap phases).
- Until the knowledge repo is built, its starting checklist is `## For knowledge` in `notes/ideas.md` (from 40); most learning decisions are made in that repo, not here.
- Tracker: local markdown (`docs/agents/issue-tracker.md`, "Wayfinding operations"). Decision tickets are `decisions/NN-*.md` (never `issues/`, which holds work tickets from `/to-tickets`).
- Since 2026-11-25 the toolbox's `/ship` skill is `/open-pr` (it clashed with Claude Code's built-in `/ship`, issue #16). Tickets written earlier still say `/ship`; read it as `/open-pr`. Topic names such as "15 ship and after" and the ship stage keep the word.
- Until 42 is built, **this repo acts as home**: sessions start here, the idea Inbox and `## For home` live in `notes/ideas.md`, and `## For home` is 42's starting checklist.
